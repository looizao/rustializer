# Recreate the serializer engine in Rust

Rustializer will recreate DRF's serializer machinery in Rust while exposing compatible Python objects to existing applications. We chose this over retaining DRF's Python implementations and accelerating selected loops because the intended scope is a complete engine recreation.

The boundary includes DRF-owned serializers, fields, relations, validators, model field generation, defaults, errors, and lifecycle/persistence orchestration. DRF-owned classes will be native Rust-backed Python classes throughout, rather than thin Python facade classes delegating to a Rust engine. Native classes may share storage through common ancestors and expose ordinary Python instance dictionaries for mutable attributes and application-added state. Django's ORM, application callbacks, and custom Python fields continue executing through Python. Parsers, renderers, views, authentication, and routing remain outside the port. Native construction must preserve metaclass behavior, shared layouts, and Python callback dispatch; these will first be checked by the Stable ABI feasibility milestone. Preservation of existing application behavior remains mandatory.

Compatibility preserves application-facing serializer behavior, including values, Python value types, errors, signatures, inheritance, hooks, mutation, and side effects. Python bytecode, `__code__`, source inspection, and internal traceback frames are explicitly excluded because native implementations differ from Python functions in these respects.

Compatibility evidence will require the unmodified upstream suite against the activated replacement across every agreed runtime combination; targeted tests for activation, import order, dynamic fields, subclassing, and hooks; differential checks of values, Python types, errors, callback order, and database effects; and installation/integration checks of the built distribution. Performance measurements may establish a baseline during development, but optimization follows the compatibility gate.
